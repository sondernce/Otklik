# Резервные копии и восстановление

Команды выполняются из `otklik/`. Инструмент `backup.py` работает локально и не доступен через сайт. В копию входят все данные SQLite: аккаунты, фотографии, встречи, переписка, обращения и уведомления. Шифрование копий и отправка во внешнее хранилище пока не подключены. Автоматическое расписание и удаление старых копий не настроены.

## Создание копии

```sh
python3 -B backup.py create --database .local/otklik.sqlite3 --output .local/backups/otklik-2026-11-17.sqlite3
```

Сервер можно оставить работающим. Инструмент использует SQLite Backup API, поэтому учитывает подтверждённые изменения из WAL и не включает незавершённые транзакции. Обычное копирование одного файла работающей SQLite этого не гарантирует.

Имя файла назначения должно быть новым. Инструмент не заменяет существующий файл, даже если его одновременно создал другой процесс. Копия сначала записывается во временный файл в той же папке, проверяется, затем становится доступной под указанным именем. При ошибке временный файл удаляется. На Linux новые файлы базы и копии создаются с правами `0600`.

Результат содержит путь, версию схемы, количество встреч и SHA-256 файла. Он не содержит сообщений, паролей или токенов сессий. Подключение для чтения не создаёт базу при ошибке в пути.

## Проверка

```sh
python3 -B backup.py verify .local/backups/otklik-2026-11-17.sqlite3
```

Проверяются `integrity_check`, внешние ключи, поддерживаемая версия схемы и наличие таблиц приложения. Команда возвращает ненулевой код завершения при ошибке. SHA-256 можно сохранить отдельно, чтобы позже сравнить его с результатом повторной проверки. Проверка целостности не заменяет пробное восстановление.

## Восстановление

```sh
python3 -B backup.py restore --backup .local/backups/otklik-2026-11-17.sqlite3 --output .local/restored-2026-11-17.sqlite3
```

Восстановление создаёт отдельную базу, исходная копия и рабочий файл сохраняются. При необходимости схема новой базы обновляется до текущей версии. Файлы с неизвестной более новой версией не принимаются.

Все сессии в восстановленной базе удаляются. Участникам потребуется войти заново: восстановление не должно возвращать доступ по токену, отозванному после создания копии. Аккаунты и пароли сохраняются. Сессии в исходной рабочей базе не изменяются.

Чтобы проверить или использовать восстановленную базу, остановите прежний сервер и запустите приложение с новым путём:

```sh
OTKLIK_DB=.local/restored-2026-11-17.sqlite3 python3 server.py
```

После входа проверьте встречи и переписку. Не удаляйте прежнюю базу до завершения проверки. Остановка нужна при переключении приложения, сама команда восстановления работает с отдельным файлом.

## Что проверено тестами

Восстановление встреч, диалогов, обращений, уведомлений и видеоссылок; прекращение прежних сессий; миграция копии версии 5; копирование работающей базы в WAL; отказ при повреждении или нарушении связей; сохранность существующего файла; одновременное создание одной копии; очистка временного файла при ошибке. Рабочая пользовательская база в этих тестах не используется.

## Сведения в кабинете администратора

Успешный запуск `create` сохраняет дату создания и проверки в служебном файле рядом с рабочей базой. Для `verify` и `restore` можно указать `--record-for /path/to/working.sqlite3`, чтобы отметить проверку для нужного кабинета. Рабочая SQLite при записи этой отметки не меняется. Если отметка недоступна, результат копирования сохраняется, а JSON содержит `monitoring_warning`. Автоматического расписания по-прежнему нет. [Подробности мониторинга](admin-monitoring.md).

Начиная со схемы 8, восстановление также отменяет незавершённые задания почтовой очереди и очищает содержимое писем в новом файле. Старые письма из копии автоматически не отправляются; исходная база не меняется.
